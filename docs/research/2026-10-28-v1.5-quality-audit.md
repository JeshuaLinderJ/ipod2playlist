### 5. Legibility (found by reading)
The code is small, plainly named and mostly explicit, and comments explain *why*. spotify.py and youtube.py are parallel and short, with almost no duplicated logic. The specific nits are in M9. The one structural point is in cli.py: error handling uses three styles. `_load_*` uses `SystemExit(msg)`, `_build_service` checks a file up front, and `main` uses print plus `SystemExit(2)`. Spotify-side and auth errors are not handled at all (I3).

### 6. Robustness at the seams (verified by running)
- **5,000 songs** (`/tmp/qa/scripts/bench_progress.py`): `progress.save()` rewrites the whole file after every song, so total cost is O(n²). Measured:
  - 1k songs: 0.76 s total
  - **5k songs: 11.3 s total**, last save 34 ms, file 366 KiB, about 0.9 GB written overall
  - 20k songs: 161 s

  A 5k run makes about 15k HTTP calls, which take tens of minutes, so the saves add under 1%. Not worth fixing (M10).
- **Other 5k-song costs:** `dedupe` of 10k songs took 5 ms and `best_match` ×5000 took 0.38 s. Nothing else is quadratic.
- **Non-ASCII and emoji:** Icelandic, Japanese and emoji tags survive the scan, `songs.json` (UTF-8, `ensure_ascii=False`) and matching (`score("東京","くるり")=100`, `"Jóga 🎵"` matches `"Jóga"`). Two problems:
  - Tabs and newlines in tags corrupt `songs.tsv` (M1).
  - NFC and NFD spellings of the same song are not deduped (M7).
- **iPod path with spaces or an apostrophe:** works (`/tmp/qa/Volumes/Jo's iPod`, and `--songs "Jo's dir/my songs.json"`).
- **Older songs.json:** the v1 `ipod_song_list.json` (same four keys in a different order) loads and syncs with `--songs ipod_song_list.json`. An extra or missing key gives a clean "not a valid song list" message. A null artist or a numeric title crashes with a traceback (M6).
  - v1 used the filename *with* extension as the fallback title (`QRST.mp3`), while v1.5 uses the stem. Untagged songs therefore get different keys, which is harmless because v1 had no progress file.

### Important

**I1. "Delete progress.json" advice destroys the other service's state and creates duplicate playlists**
`README.md:97-98`, `cli.py:99-100`, design in `progress.py` (one file for both services) — *verified by running* (`/tmp/qa/scripts/delete_progress_trap.py`)
- **Scenario:** the user deletes only the YouTube playlist, then follows the advice and deletes `progress.json`.
- **Evidence:**
```
# re-run youtube --only-spotify-missing:
0 added / 0 missing / 0 skipped / 0 failed          <- the Spotify "missing" list is gone, so nothing is selected
# re-run spotify:
1 added / 6 missing / 0 skipped / 0 failed
Spotify playlists now: [('My iPod Playlist', 1), ('My iPod Playlist', 1)]   <- duplicate playlist
YouTube playlists now: [('playlist1', 1), ('playlist2', 0)]                <- new empty playlist
```
- **User impact:** a non-expert loses days of YouTube-quota progress. They also get a second Spotify playlist after re-searching every song, and `--only-spotify-missing` silently does nothing.
- **Fix (simple):** change the hint and README to "delete the `"youtube"` (or `"spotify"`) block inside progress.json". Alternatively, make `sync` treat a playlist-not-found error from `add` as "playlist gone": clear only that service's `playlist_id`, save, and exit with a message to re-run.

**I2. A stale or deleted YouTube playlist burns the whole daily quota every run**
`sync.py:32-42` — *verified by running* (`/tmp/qa/scripts/deleted_yt_playlist.py`)
- **Evidence:** `progress.json` still holds a playlist id that no longer exists. Each song still pays for a 100-unit search before its `add` fails. The failure is left unrecorded, so tomorrow repeats it:
```
SyncResult(added=0, missing=0, skipped=0, failed=66) searches: 66 quota units burned ~ 9900 of 10000
```
- **User impact:** someone who follows the README's "re-run it the next day" makes no progress, ever. The hint appears only at the end, after the quota is spent. The same loop also spins through every remaining song on any persistent error, such as revoked auth or network down, printing one `! failed` line per song.
- **Fix:** stop the run on the first add that fails with 404/`playlistNotFound` (same handling as I1). Or stop after a few consecutive failures with the existing hint.

**I3. First-run mistakes end in raw tracebacks; YouTube secrets are the only handled case**
`cli.py:51-58`, `cli.py:112-121`, `sync.py:21-24` (create is outside the per-song `try`) — *verified by running* (installed wheel, and `/tmp/qa/scripts/seams.py`)
- **Evidence:**
  - No or misnamed `.env` (e.g. `.env.txt`): `spotipy.exceptions.SpotifyOauthError: No client_id. Pass it or set a SPOTIPY_CLIENT_ID environment variable.` after a 20-line traceback.
  - Spotify 403 on playlist create (a development-mode app used by an account not added to the app, which is the "favour for family" case): `UNCAUGHT SpotifyException: http status: 403 … the user may not be registered.`
  - YouTube non-quota error on create (e.g. `youtubeSignupRequired`): `UNCAUGHT HttpError 403`.
- **User impact:** the README targets newcomers, and these are their most likely first errors. The YouTube missing-secrets case already exits cleanly, so the behaviour is inconsistent.
- **Fix:** in `main`, catch `spotipy.SpotifyOauthError`/`SpotifyException` and `googleapiclient.errors.HttpError` and exit with one line each, pointing to README step 2 or 3. Keep it to one `except` per library.

**I4. CLI flags the README relies on are untested; several behaviours could break with all tests green**
`tests/test_cli.py` (whole file), `tests/test_youtube.py`, `tests/test_matching.py` — *verified by mutation*
- **Evidence:** the mutation list above. `--songs`, `--progress`, `--public` and `--retry-missing` can all be ignored by `cli.py` and every test still passes.
  - README step 6 depends on `--songs` and `--progress` to keep the dry run out of the real `progress.json`. If they were ignored, the test songs would be recorded as done in the real file.
  - The `RefreshError` re-login, `scan`'s `is_file()` guard and title-scoring strictness (`ratio` → `partial_ratio`, which would match "Yesterday" to "Yesterday Once More") are also unpinned.
- **User impact:** regressions in the paths the README walks a newcomer through would ship unnoticed.
- **Fix:** add one CLI test that runs with `--songs x.json --progress y.json --public --retry-missing` and asserts the outcome: files touched, `fake.playlists[0]["public"]`, and re-searched count. Add a matching test for a different song whose title starts with the wanted title. Add a `make_client` test with monkeypatched `Credentials` and `InstalledAppFlow`.

### Minor

**M1. Hand-rolled TSV breaks on tabs and newlines in tags.** `library.py:43-46` — *verified by running*.
- A title `Tab\there` and artist `New\nLine` produce a row split across two lines with five columns, which shifts every column in the spreadsheet the README asks the user to check.
- *Fix:* `csv.writer(f, delimiter="\t")` (reuse the library; it quotes such fields).
- *Found by reading, not verified:* Excel often misreads UTF-8 without a BOM. Consider `encoding="utf-8-sig"` for the TSVs.

**M2. Python 3.10 prints a FutureWarning on every command.** `pyproject.toml:6`, `README.md:8` — *verified by running* `/tmp/qa/venv310/bin/ipod2playlist --help`:
`FutureWarning: You are using a non-supported Python version (3.10.13). Google will not post any further updates to google.api_core …`
- This is alarming for non-experts.
- *Fix:* set `requires-python = ">=3.11"` and README "3.11 or newer". uv will fetch it.

**M3. The version-word gate compares sets, so a live version of a song whose title already contains "live" is accepted.** `matching.py:61-64` — *verified*: `score("Live and Let Die" vs "Live and Let Die (Live)") = 86.5`. That passes the threshold and contradicts the README's "live … versions are never swapped in".
- Related: the band **Live** never matches on YouTube (`score = 0`), because "live" appears in the video title but not the song title.
- *Fix:* compare `collections.Counter`s instead of sets, and strip a leading "Artist - " before the version check.

**M4. Strict gates reject common YouTube titles and cost quota.** `matching.py:55,58` — *verified*. Each of these scores 0:
- `"Blur - Song 2 (Official Music Video) [4K]"` (the "4" in [4K] fails the digit gate)
- `"Queen - Bohemian Rhapsody (1975)"` (a year in brackets)
- Spotify `"Beatles"` against an iPod tag `"The Beatles"` (`ratio = 78 < 85`)

These fail safe (the song goes to the missing list), but each failure wastes 100 quota units.
- *Fix:* treat `4k` and a bracketed year as noise, and strip a leading "the " in the artist gate. Add tests for each.

**M5. An empty YouTube playlist is created when there is nothing to sync.** `sync.py:21-24`, `cli.py:91-93` — *verified*.
- `youtube --only-spotify-missing` before `spotify` has ever run creates a playlist (50 units) and prints `0 added / 0 missing / 0 skipped / 0 failed` with no explanation.
- *Fix:* if `songs` is empty, print "no songs to process (run `spotify` first?)" and return before creating anything.

**M6. Malformed input files give tracebacks instead of the friendly messages.** `cli.py:61-74`, `library.py:20`, `progress.py:15`, `cli.py:82` — *verified*.
- `progress.json` containing `{}` → `KeyError: 'services'`. Containing `[]`, or a songs.json passed by mistake → `TypeError`.
- A songs.json entry with `"artist": null` or `"title": 1999` (easy to produce when hand-editing `tiny.json` as README step 6 asks) → `AttributeError … casefold`.
- `scan --songs out/songs.json` where `out/` does not exist → `FileNotFoundError`.
- *Fix:* catch `(KeyError, TypeError, AttributeError)` alongside the existing exceptions in `_load_progress`/`_load_songs`. Check that the `--songs` parent directory exists in `_scan`.

**M7. Dedupe and progress keys do not Unicode-normalize.** `library.py:7-8` — *verified*: NFC `"Jóga/Björk"` and NFD `"Jóga/Björk"` are not deduped. Matching itself does normalize.
- *Fix:* `unicodedata.normalize("NFC", text)` in `_norm`.

**M8. Small CLI surface mismatches.** `cli.py:24-29`, `cli.py:42-44` — *verified via `--help`*.
- `scan` accepts `--progress` but never uses it, which is dead code.
- `--client-secrets` and `--token` have no help text.
- The `YOUTUBE_CLIENT_SECRETS` env var is an undocumented extra feature. Drop it or document it.

**M9. Legibility nits.** *Found by reading.*
- `scan.py:17` `return values[0].strip() or None if values else None` relies on operator precedence and is the cleverest line in the codebase. Write it as an explicit `if`.
- `scan.py:22-30` sets `reason` in a `try/except/else` before checking `None`, which reads backwards. Two explicit early returns would be clearer.
- `cli.py:34-44` uses a loop over `("spotify", "youtube")` with an `if name == "youtube"` special case. Two explicit blocks would read better. `add_command(name, help)` also shadows the builtin `help`.
- `cli.py:91` `getattr(args, "only_spotify_missing", False)` hides that the flag belongs only to `youtube`. Use `args.command == "youtube" and args.only_spotify_missing`.
- `sync.py:16` has no type hints, unlike the rest of the code. It also imports `QuotaExceeded` from `youtube`, so the generic loop depends on one service. Move the exception to `sync.py` or a small `errors` spot.
- `matching.py:43` docstring line is about 130 characters (an inserted clause). The `85` and `80` thresholds should be named constants.
- `progress.py:13` writes `"version": 1` but nothing ever reads it.

**M10. Per-song full rewrite of progress.json.** `sync.py:52`, `progress.py:38-43` — *measured*: 11.3 s cumulative for 5,000 songs, which is negligible next to network time. There is no `fsync`, so the save is atomic but not durable on power loss. **No action recommended**; this is noted for completeness.

**M11. Ctrl-C prints a `KeyboardInterrupt` traceback**, though the README says "You can stop and re-run anything". `cli.py:116-121` — *found by reading*.
- *Fix:* `except KeyboardInterrupt: print("Stopped; progress saved. Re-run to continue."); raise SystemExit(130)`.

**M12. Fakes are looser than the real APIs, and some tests assert fake behaviour.** `tests/fakes.py:22-33,96-98`, `tests/test_spotify.py:14-19`, `tests/test_youtube.py:54-59`, `tests/test_progress.py:84` — *verified*.
- `FakeYouTube.list` ignores `q` and accepts any keyword. The real discovery client rejects a typo: `real client, typo param -> Got an unexpected keyword argument maxresult`, while the fake accepts it silently.
- `FakeSpotify` treats `track:"…"` as an exact match. Real Spotify field filters are fuzzy, so `test_strict_hit_returns_only_exact_match` tests the fake, not `SpotifyService`. The "strict search removed" mutation survives.
- `FakeSpotify.playlist_add_items` accepts any string, whereas spotipy validates URIs. The test URIs like `spotify:track:Hey Jude` would be rejected by the real client.
- **Implementation-coupled tests:**
  - `test_end_to_end…` and `test_quota_error…` count `execute()` calls (`fail_after=3/5`).
  - `test_failed_write_leaves_existing_file_intact` monkeypatches `json.dump`, so it would fail if `save` switched to `json.dumps`.
  - `test_quota_hit_partway_through_keeps_earlier_work` asserts nothing about "earlier work".
- *Fix:* for YouTube, replace the hand-written fake with real `build("youtube", "v3", http=HttpMockSequence(...), static_discovery=True)`, which works offline. For Spotify, use real `spotipy.Spotify` with a mocked session. `/tmp/qa/scripts/real_clients.py` shows both; this reuses the libraries rather than reimplementing them.

**M13. A `None` entry in Spotify search items would count as a per-song failure forever.** `spotify.py:22-28` — *verified* that `[None, track]` raises `TypeError`, which is caught as `failed`. *Unverified* how often real Spotify returns nulls here.
- *Fix:* `for item in items if item`.

**M14. Untagged songs (all WAVs) are still searched.** `scan.py:34`, `sync.py:33` — *found by reading*.
- `"Unknown Artist - QRST"` can never pass the artist gate but costs 100 YouTube units each.
- *Fix:* record songs whose artist is `"Unknown Artist"` as missing without searching, or skip them in `scan` with a note.

## What's good
- **It works.** Through the real spotipy (2.26: `/me/playlists`, `/playlists/{id}/items`) and googleapiclient (static discovery) libraries, every service call builds correct requests. Quota detection fires on a realistic error body.
- **Tests are fast and the core is well covered.** The suite takes 0.4 s with 94% branch coverage. Sync, progress, quota/resume and the matching false-positive cases (covers, karaoke, live, "U2" inside a channel name) are well covered.
- **Careful details:** atomic progress writes, token file forced to `0600` even when it already exists, `.env` loaded from the user's cwd (so `uv tool install` works), and `ensure_ascii=False` for songs.json. AppleDouble `._` files and the iTunesDB are skipped, and the scan does not clobber `songs.json` when the iPod is not mounted.
- **The README is accurate.** Its messages and filenames match the code character for character. The v1 song list loads unchanged.
- **The code is small and plain** (346 statements), with clean single-purpose modules and comments that explain *why*. Pyright reports zero issues, and ruff findings are noise only.
